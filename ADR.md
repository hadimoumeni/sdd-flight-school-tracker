## 1. Backend framework: Flask
Date: 2026-10-02
Status: Decided
Context: Needed a backend framework for a single-process app with a small, well-understood surface (routes, SQLite, server-rendered pages). The comprehension check requires explaining every line cold.
Decision: Flask. Minimal and unopinionated — a route is a function, nothing is generated or hidden.
Alternatives considered: FastAPI, for typed request/response models and auto-generated docs. Rejected: neither feature pays for itself in a one-person, no-public-API app, and it's more surface to defend on paper than Flask buys back.
Consequences: No automatic request validation or docs — anything like that has to be written by hand if ever needed. In exchange, the whole request/response cycle fits in a few lines I wrote myself.

## 2. Two domains kept independently modularizable
Date: 2026-10-02
Status: Decided
Context: The assignment requires two backend feature domains coupled as little as possible, each able to point to where a future microservice split would go.
Decision: Scheduling and Maintenance live in separate packages (domains/scheduling, domains/maintenance) with their own service modules. Scheduling calls Maintenance only through one function, `is_airworthy(conn, aircraft_id)` — it never reads the aircraft/squawks tables directly.
Alternatives considered: Scheduling querying aircraft/squawk tables directly (join in SQL) to compute airworthiness inline. Rejected: it's less SQL, but it duplicates the grounding rule in two places and gives no single seam to cut along later.
Consequences: One extra function call per booking, and any new grounding rule only needs to change in one place (`is_airworthy`). The day this splits into two services, that function becomes the one HTTP call between them.

## 3. Lessons reference aircraft/students/instructors by foreign key, not duplicated data
Date: 2026-10-09
Status: Decided
Context: A lesson needs to know which student, instructor, and aircraft it's for, and the scheduling conflict check needs to query by instructor/aircraft efficiently.
Decision: `lessons` stores `student_id`, `instructor_id`, `aircraft_id` as foreign keys into `students`, `instructors`, `aircraft`. `squawks` stores `aircraft_id` as a foreign key into `aircraft`. No table duplicates another table's columns.
Alternatives considered: Storing a denormalized snapshot of student/instructor name on each lesson row (so the lesson record is self-contained even if the student is later renamed/deleted). Rejected: nothing in this app needs a lesson to survive a renamed or deleted student, and it would mean updating N lesson rows every time a student's name changes.
Consequences: Every lesson/squawk listing needs a JOIN to show human-readable names (see `domains/scheduling/routes.py`'s `index`). In exchange, there's exactly one place each piece of data lives.

## 4. Testing approach: business logic gets tests, routes get a manual run
Date: 2026-10-09
Status: Decided
Context: The assignment asks for ≥70% coverage on core business logic, explicitly excluding "framework glue or routing." Both domains' real logic (airworthiness, booking conflicts) lives in `service.py`; `routes.py` just reads a form, calls a service function, and redirects.
Decision: `domains/*/service.py` is unit-tested against an in-memory SQLite connection, built test-first (TDD): write the test, watch it fail, then write the minimum code to pass. `domains/*/routes.py` has no automated tests; each route was exercised once by hand over real HTTP (create student/instructor/aircraft, book a lesson, report a squawk, confirm a grounded aircraft rejects a booking) before being committed.
Alternatives considered: Using Flask's test client to write route-level tests too, for a higher overall coverage number. Rejected for now — it would mostly re-test the same conflict/grounding logic through an extra HTTP layer, for coverage on code the assignment doesn't grade.
Consequences: `pytest --cov=domains.maintenance.service --cov=domains.scheduling.service` reports 100%, honestly scoped to the code that's actually graded. If a route grows real logic of its own later, that logic should move into a service function and get the same test treatment — not stay untested in the route.

## 5. No login/authentication
Date: 2026-10-11
Status: Decided
Context: The stakeholder is a small flight school with one shared front-desk terminal and no public-facing users; §1b lists auth as a free choice to justify either way.
Decision: No login, no sessions, no user accounts. Every route is reachable by anyone who can open the app, the same as a shared terminal at a front desk.
Alternatives considered: Role-based auth (student/instructor/admin), which was the original design-phase idea. Rejected for this submission: it adds real surface (password storage, session handling, route guards) that has nothing to do with the two required feature domains, and risked eating the time budget needed for the scheduling/maintenance logic and its tests.
Consequences: Anyone with the URL can book lessons, add aircraft, or resolve squawks — fine for a single trusted terminal, not fine if this were ever exposed beyond that. Adding auth later means wrapping existing routes in a guard decorator, not restructuring the domains themselves.

## 6. The split: maintenance and scheduling as two services
Date: 2026-11-17
Status: Decided
Context: Assignment 2 requires one service per feature domain, each with its own container and database, talking over HTTP. ADR-2 drew the seam at a single function, `is_airworthy(conn, aircraft_id)`, the only place scheduling reached into maintenance.
Decision: The seam held exactly where ADR-2 put it. `services/maintenance` owns `aircraft` and `squawks`; `services/scheduling` owns `students`, `instructors` and `lessons`. Two flows cross it server side: booking a lesson calls `GET /aircraft/{id}/airworthiness`, and completing a lesson calls `POST /aircraft/{id}/flight-hours`. Showing tail numbers next to lessons is done client side: the UI reads both services and joins on `aircraft_id`. If maintenance does not answer within `MAINTENANCE_TIMEOUT_S` (2 s), scheduling fails the request with 503 and a clear message, and the lesson is not booked or completed.
Alternatives considered: Degrading instead of failing (book the lesson anyway and check airworthiness later). Rejected: airworthiness is a safety rule, so booking a grounded aircraft is worse than refusing a booking for a minute. Caching the last airworthiness answer was rejected for the same reason: a squawk reported a second ago must ground the aircraft now.
Consequences: Scheduling keeps serving students, instructors and lessons while maintenance is down; only booking and completing stop, with a message that says why. `lessons.aircraft_id` is now a plain ID with no foreign key, so a lesson could point at an aircraft that no longer exists; aircraft are never deleted, so this cannot happen today (see ADR-7). The completion flow logs hours before marking the lesson completed, so if maintenance is down the lesson stays scheduled and can be retried.

## 7. Data and migrations: one database per service, numbered SQL files
Date: 2026-11-20
Status: Decided
Context: Assignment 1 kept all five tables in one SQLite file and created the schema with `CREATE TABLE IF NOT EXISTS` on boot. After the split each service needs its own SQL Server database, and once a database holds data its schema has to change in place.
Decision: Maintenance owns `aircraft` and `squawks` in its own database; scheduling owns `students`, `instructors` and `lessons` in another. Each service logs in with its own login, which is `db_owner` on its own database only (`db/init.sql` locally). The schema is defined by numbered SQL files in `services/<name>/migrations/`. On startup, `db.py` applies every file not yet listed in `schema_migrations`, in name order, each in one transaction together with its `schema_migrations` row. Files are split on `GO` lines because SQL Server cannot use a column in the same batch that adds it. Migration 002 shows the rule in practice: it adds `lessons.completed_at` as NULL to a table that already holds data and backfills completed lessons with their end time. Applied files are never edited; corrections go in a new file. No data was moved: the Assignment 1 SQLite file only ever held test data, so both databases start from `001_init.sql`. If real data had existed, each table would have been copied into the database of the service that owns it, keeping the same ids (`SET IDENTITY_INSERT`) so `lessons.aircraft_id` still matches.
Alternatives considered: Alembic, which tracks versions the same way but adds a dependency and model or revision files. Rejected: the services already use plain SQL in `store.py` with no ORM models, and the runner is about 30 lines I can explain line by line. A NOT NULL `completed_at` with a default was also rejected, since there is no true completion time for old lessons; NULL plus a backfill from `end_time` is honest about that.
Consequences: The foreign key from `lessons.aircraft_id` to `aircraft` is gone, because the two tables are in different databases. It is compensated in code: booking asks maintenance for the aircraft first (404 becomes "unknown aircraft"), and there is no way to delete an aircraft, so a lesson cannot point at one that disappeared. Recovery plan for a bad migration in production: (1) a file that fails is rolled back completely and not recorded, the container exits, and the post-deploy health check fails the run, so the fix is a corrected new migration in the next commit; (2) a migration that runs but is wrong is corrected by a new migration, forward only; (3) if data was damaged, restore the database to a point in time before the deploy from Azure SQL's automated backups. The passwords in `docker-compose.yml` are throwaway local defaults for a container on the developer's machine; the Azure database passwords exist only as GitHub Actions secrets.

## 8. Serverless hosting on Azure: Container Apps, serverless SQL, a storage website
Date: 2026-11-21
Status: Decided
Context: The brief requires everything on my Azure for Students subscription and billed only per use, so nothing costs money while the app is idle. The infrastructure is either Azure CLI commands in the workflow or IaC.
Decision: Bicep (`infra/main.bicep` and `infra/container-app.bicep`), deployed by the CD workflow on every push to `main`. The resources are: a Log Analytics workspace for the containers' logs; one Container Apps environment on the Consumption plan; two Container Apps with public HTTPS ingress and 0 to 1 replicas, whose `DATABASE_URL` is a Container Apps secret; one SQL server with one General Purpose serverless Gen5 database per service (0.5 to 1 vCore, free offer, locally redundant backups); and one storage account whose static website serves `ui/`. Images live in GHCR. The few things the pipeline's identity cannot or should not do (assign its own role, create SQL logins as admin, write GitHub secrets) are in `infra/setup.sh`, run once by me.
Alternatives considered: Azure CLI commands in the workflow. Rejected: they say how to change things, not what should exist, so running them twice can fail or drift; a Bicep deployment is incremental and only changes what differs, and the whole environment can be read in two files. Azure Container Registry was rejected because it has a fixed monthly cost; GHCR is free.
Consequences: Cost model: Container Apps bill per second of vCPU and memory while a replica runs (with a monthly free grant), so 0 replicas means nothing is billed. The free SQL offer covers a monthly amount of compute per database, auto-pauses after 60 minutes idle, and pauses instead of billing if the free amount runs out. Storage and Log Analytics cost cents per GB, and Log Analytics is free under 5 GB a month. Scale to zero has a price. The first request after idle starts a container (Container Apps answers 503 after about 30 s if it is not ready yet). If the app was idle for over an hour, the database is paused too and takes up to a minute to resume, refusing connections meanwhile (error 40613). `db.py` handles this with `wait_for_database`, which retries with backoff (2, 4, 8, 16, 30 s...) before running migrations. The UI turns the 503 into "starting up, press Retry", and the post-deploy health check waits up to 6 minutes. Running migrations at startup is safe only because there is at most one replica, so two copies can never apply the same file at once. At 100x traffic I would change four things. First, raise `maxReplicas`, which means moving migrations out of container startup into a separate pipeline step (or taking a lock) so replicas cannot race. Second, keep `minReplicas` at 1 so users never hit a cold start. Third, leave the free SQL offer for more vCores, and check that the connection pool size times the replica count stays under the database's connection limit. Fourth, watch the Log Analytics volume, which would pass the free 5 GB.

## 9. Pipeline and testing: unit tests on the rules, one real cross-seam stack in CI
Date: 2026-11-24
Status: Decided
Context: Every push must be tested, and only a commit that passed CI may be deployed. The brief also asks for at least one integration test across the seam, run either against the compose stack or with the other service replaced by a stub.
Decision: CI (`ci.yml`) runs on every push and PR and gates on six things. (1) `ruff check` and `ruff format --check` per service. (2) `pytest` per service with `--cov-fail-under=70` on the core logic (`logic.py`, plus `maintenance_client.py` in scheduling). (3) A `docker build` of each image. (4) Validation of each `openapi.yaml` and of `system.yaml` against `system.schema.json`. (5) A compile of the Bicep and `shellcheck` on the setup script. (6) The cross-seam integration tests in `tests/integration/`, run against the real compose stack (SQL Server in a container, both services, nothing stubbed). They book through scheduling, which asks maintenance for airworthiness. They check that a safety squawk blocks booking, that completing a lesson adds hours in maintenance, and that the real responses match maintenance's OpenAPI document. Finally they stop maintenance and check that booking returns 503 in under 5 s while scheduling keeps serving. CD (`cd.yml`) is triggered by `workflow_run` when CI completes on `main`, and deploys only if that run succeeded on the same `head_sha`.
Alternatives considered: A stub of maintenance for the cross-seam test. Rejected: it would only test my own assumptions about maintenance's answers, while the real stack also tests the SQL Server migrations, the HTTP contract and a real timeout, for about one minute of CI time. For CD, the course guide suggests calling `ci.yml` with `workflow_call`; `workflow_run` gives the same guarantee (CI passed on that exact commit) without running CI twice.
Consequences: Unit coverage is measured on the business rules only. Routes (`app.py`) and SQL (`store.py`) are glue, covered by the integration tests rather than mocked unit tests. Deliberately not tested in CI: the UI's JavaScript (checked by hand in headless Chrome, screenshots in `docs/evidence/`); anything on Azure, because CI must never touch Azure SQL and every connection would wake and bill it (so cold starts, error 40613 and the real deployment are only checked by the post-deploy health check); and load or performance. No CI run has failed so far: the gates caught nothing because every change was checked locally first (one real mistake, an unquoted comma in an OpenAPI description, was caught by the validator before pushing).
